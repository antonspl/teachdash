# Design

## Context

See `proposal.md` for motivation, the engineer's decisions and the research.

- Today: `CLAUDE.md` (43 lines) mixes process rules with Claude agent wiring. `.claude/agents/` holds four roles, all with `model: sonnet`. Their tools today:
  - researcher: `Read, Grep, Glob, Bash, WebSearch, WebFetch`.
  - spec-critic and reviewer: `Read, Grep, Glob, Bash`.
  - implementer: no `tools` field, so full access.
- `.claude/skills/` holds six skills generated by OpenSpec 1.15. `.claude/commands/opsx/` is empty.
- The constitution is 12 KB. Today the agent reads all of it at the start of every session.
- `scripts/` holds only `check-scenario-coverage.sh`.
- `openspec update` detects tools by their folders. Tested on a copy of the repo on 2026-11-17:
  - with only `.agents/skills/` present, it wrote only there;
  - with both `.agents/skills/` and `.claude/skills/` present, it wrote to both.

## Goals / Non-Goals

**Goals:**

- A developer with any of the three tools follows the same process after one setup command.
- Losing access to one model provider needs only a change to the personal model map.
- Each role and each rule is written in one place.

**Non-Goals:**

- Identical behaviour across tools. Codex cannot enforce read-only roles.

## Decisions

### D1. `AGENTS.md` is the single instruction file

`AGENTS.md` holds every rule from today's `CLAUDE.md` in neutral words:

- the orchestrator role and the agent rules;
- the three reviewer triggers: after every pass 2 slice, on implementer doubt, and the code-gate review once per PR;
- the git flow, including "never merge, never push to `main`, never force-push";
- that the agent never ticks a gate box and never writes an approval comment.

It also holds a constitution summary of about 30 lines: the gates, the roles, and which section to read before which step. Its first rule says: if the tool's agent folder is missing, or `scripts/setup-agents --check` reports it stale, run `scripts/setup-agents` and restart the session.

`CLAUDE.md` contains only `@AGENTS.md`.

The file stays well under Codex's 32 KiB cap. Codex has no imports, so the constitution is not inlined. The agent reads it by section. This replaces the old rule "Read `openspec/constitution.md` before any work": `AGENTS.md` has a table of which section to read for which step, and §1 is read for any step.

- Alternative: symlink `CLAUDE.md` to `AGENTS.md`. Rejected. The import is enough.

### D2. Neutral role sources in `.agents/roles/`

There is one Markdown file per role. The body is the prompt. The frontmatter holds:

- `name` and `description`;
- `class`: `strong` or `medium`;
- `access`: `read` or `write`;
- `web`: `true` or `false`.

| Role | class | access | web |
|---|---|---|---|
| researcher | medium | read | true |
| spec-critic | medium | read | false |
| implementer | medium | write | true |
| reviewer | medium | read | false |
| code-gate-reviewer | strong | read | false |

The code-gate reviewer is a separate role because opencode and Codex cannot override the model per call. Claude Code can, and that is how today's per-PR review runs: `reviewer` with `model: "opus"`. The prompt is the reviewer prompt plus the per-PR scope. It also says that in some tools nothing stops it from editing files, so it must not.

Descriptions name no model or tool.

`.agents/` is chosen because Codex and opencode already use it for skills.

### D3. Personal model map

`.agents/models.local` is gitignored. It has one line per tool and class:

```
claude.strong   = opus
opencode.medium = anthropic/claude-sonnet-5-5
codex.strong    = gpt-6.2-sol high
```

The optional second word is the reasoning effort, used only by Codex. `.agents/models.example` is committed. It shows the format with Anthropic and OpenAI examples, as the docs showed them on 2026-11-17.

When a class has no entry for a tool, the generated agent has no model field (Codex: neither `model` nor `model_reasoning_effort`). The role then runs on the session's model, which all three tools inherit when the field is omitted (research angle 4).

- Alternative: model IDs committed in the repo. Rejected. In opencode and Codex a repo value beats the user's config, so a developer without that provider would be stuck.
- Alternative: no classes. Rejected. The code-gate review should run on a stronger model than the per-slice reviews.

### D4. `scripts/setup-agents` generates per-tool files

It is written in POSIX shell with `awk`, and needs no new dependency (constitution §7). For each role it writes:

| Tool | Path | Mapping |
|---|---|---|
| Claude Code | `.claude/agents/<name>.md` | `model` from the map. `access: read` gives `tools: Read, Grep, Glob, Bash`, plus `WebSearch, WebFetch` when `web: true`. `access: write` with `web: true` gives no `tools` field, which means full access, as today |
| opencode | `.opencode/agents/<name>.md` | `mode: subagent` and `model` from the map. The permission block denies `edit` for `access: read`, and denies `webfetch` and `websearch` for `web: false` |
| Codex | `.codex/agents/<name>.toml` | `name`, `description` and `developer_instructions` (the body), plus `model` and `model_reasoning_effort` from the map. `access: read` and `web: false` become instruction lines, because Codex has no per-agent sandbox |

It copies `.agents/skills/` to `.claude/skills/`. It deletes old generated files first, so a removed role does not linger. Every output path is gitignored.

It also writes a stamp holding a hash of `.agents/roles/`, `.agents/skills/` and the map. `--check` compares that stamp with the sources and prints `stale` or `ok`. It writes nothing.

A missing or malformed map line gives a one-line warning, and the agent gets no model. A broken role file (missing field, unknown value) makes it exit non-zero.

- Alternative: commit the generated files and add a CI drift check. Rejected by the engineer, because personal model IDs would end up in git.

### D5. Skills live in `.agents/skills/`

Codex and opencode read `.agents/skills/` natively, and `openspec update` refreshes whatever skills folders exist (see Context). With only `.agents/skills/` in git, an update on a fresh clone writes only there. On a machine that also has the generated `.claude/skills/`, the update writes the same content into both. That is harmless, because the copy is gitignored and `setup-agents` overwrites it. No OpenSpec setting changes.

Risk: opencode reads both `.claude/skills/` and `.agents/skills/`, so it may list each skill twice. Task 2.3 checks this in a real opencode run. If the skills do appear twice, the fix is one of:

- `opencode.json` turns off the Claude-compatible skill path;
- `setup-agents` skips the Claude copy for someone who uses only opencode.

The task records which fix was used.

### D6. Flow scripts

Each script lives in `scripts/flow/` and uses `set -euo pipefail`. On success it prints a few lines at most. On failure it passes stderr through and exits non-zero. GitHub JSON is filtered with `gh --jq`, so there is no `jq` dependency.

| Script | Does |
|---|---|
| `issue-brief <n>` | Prints the issue's title, labels, body and comments, without the constitution or the config |
| `change-start <name> <issue>` | Runs `setup-agents --check`, creates the branch from an updated `main`, then runs `openspec new change` |
| `pr-draft <name> <issue>` | Pushes, opens a draft PR from the template with `Closes #<issue>` and the change path, and prints the URL |
| `gate-request <gate> <range>` | Posts a comment with the range, and replaces only the line for that gate in the description's "Review ranges" section. It fails if the heading is missing. Other lines and the gate boxes stay as they are |
| `gate-status` | Prints, for each gate (`spec`, `tests`, `code`), whether there is an approving comment, who wrote it and when, and whether the box is ticked. It also flags an approval older than the latest `gate-request` for that gate |
| `pr-ready` | Marks the PR ready |

**Gate strings.** An approving comment starts with `spec approved`, `tests approved` or `code approved` (case-insensitive). Comments posted by the scripts start with a hidden marker, `<!-- flow -->`, and `gate-status` never counts them. `gate-status` only reports. The agent shows the result to the engineer, who is the one who decides. No script ticks a box or writes an approval.

**Branch guard.** Every script that writes refuses to run when `git symbolic-ref --short HEAD` fails (detached HEAD) or returns `main`. This works the same in worktrees.

**Testing.** When `FLOW_GH_FIXTURE` points to a JSON file, `gate-status` reads the PR from that file instead of calling `gh`. `scripts/flow/test` runs `gate-status` on fixtures that cover these cases:

- no comments;
- a correct approval;
- a wrong gate name;
- a box ticked with no comment;
- a comment with no ticked box;
- an approval older than the latest request;
- a marker comment.

There is no commit or push wrapper. That output is already small (research angle 3). The scripts never merge, never push to `main` and never force-push.

### D7. Permission rules

These are committed. They allow each flow script and `scripts/setup-agents` by exact path, not by folder wildcard, so a new script needs a deliberate rule. They forbid `git push --force`, `git push -f` and any push to `main` in all three tools:

- `.claude/settings.json`: `permissions.allow` and `permissions.deny`. `settings.local.json` stays personal.
- `opencode.json`: `permission.bash` rules with `allow` and `deny`.
- `.codex/rules/flow.rules`: `prefix_rule` with `decision="allow"` for the scripts, and `"forbidden"` for the pushes.

`pr-ready` and `gate-request` post under the engineer's GitHub account. They run only when the main agent reaches the matching step, which `AGENTS.md` defines.

### D8. Constitution and docs wording

- **Constitution §1.** The changes:
  - "what Claude produced" becomes "what the agent produced";
  - "the Opus review" becomes "the code-gate review", so the name does not clash with step 12, "Final review";
  - "Claude stops" becomes "the agent stops";
  - the list of workflow files becomes `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `.agents/`, `.claude/settings.json`, `opencode.json`, `.codex/` and the PR template.

  No rule changes meaning. The owner approved the edit (proposal, clarification 10).
- **`CONTRIBUTING.md`.** It gets the per-tool setup, the model map, the Codex trust step, and when to rerun `setup-agents`. Every "Claude" line becomes "the agent". The OpenSpec steps are named per tool: `/openspec-propose` in Claude Code and opencode, and `$openspec-propose` in Codex.
- **`.github/CODEOWNERS`.** The "open to any code owner" comment lists the same workflow files as the constitution. The owner-only paths do not change.

### D9. CI checks

A step in an existing CI job does three things:

- runs `shellcheck` on `scripts/setup-agents` and `scripts/flow/*` (shellcheck is preinstalled on GitHub's Ubuntu runners);
- runs `scripts/setup-agents` with no map and checks that it writes 5 agents for each tool;
- runs `scripts/flow/test`.

## Risks / Trade-offs

- [A developer pulls a role change and doesn't rerun setup] → The first rule in `AGENTS.md` and `change-start` both run `setup-agents --check`.
- [Codex ignores `.codex/` in an untrusted project] → `CONTRIBUTING.md` says how to trust the project.
- [A model ID in the map is wrong or unavailable] → It affects only that developer's sessions.
- [A tool changes its file format] → Only the generator changes.
- [A Codex read-only role edits files] → The role text forbids it, the reviewer checks `git status`, and the Codex rules forbid force push and pushes to `main`.

## Migration Plan

1. **In this PR.** `setup-agents` is written and run before `.claude/agents/` and `.claude/skills/` leave git, in the same commit. The agents and skills therefore stay available while the change is being implemented.
2. **After merge.** Each developer runs `scripts/setup-agents` once. Until they do, the first rule in `AGENTS.md` tells the agent to run it.
3. **Rollback.** Revert the PR. The old `.claude/` files come back from git.
